## Part I: Technical Lessons

### 1. Android Content URIs Are Opaque — Treat Them That Way

**Context:** HT-004, HT-008, HT-009, HT-014

Android's Storage Access Framework returns `content://` URIs that look like paths but aren't. The document picker gives you `content://com.android.providers.media.documents/document/msf%3A33`, not `Music/Darude - Sandstorm.mp3`.

**What We Learned:**
- **Never parse content URIs for metadata.** The path component is an opaque identifier.
- **Always thread the `displayName` from the picker.** It's the only human-readable filename you'll get.
- **Skip file-existence checks for content:// URIs.** The `File` class cannot introspect SAF URIs — they're resolved by the content provider, not the filesystem.

**Pattern Established:**
```typescript
// Bad: Treating URI as path
const filename = extractFromPath(uri); // Gets "msf:33"

// Good: Use picker's displayName
const filename = pickerResult.name; // Gets "Darude - Sandstorm.mp3"
```

### 2. SAF Permissions Expire — Lock Them In

**Context:** HT-018

The document picker grants *temporary* read permissions. After app termination or device reboot, those permissions evaporate. Tracks play fine on first import, then fail silently after restart.

**What We Learned:**
- **Call `takePersistableUriPermission()` immediately after picker returns.** This is the only way to retain access.
- **Native modules are sometimes unavoidable.** Expo's managed workflow doesn't expose SAF permission APIs — we built `expo-saf-uri-permission`.
- **Release permissions on track deletion.** Android limits persisted URIs (~500 per app). Clean up after yourself.

**Pattern Established:**
```kotlin
// Native module call after picker returns
context.contentResolver.takePersistableUriPermission(
    uri,
    Intent.FLAG_GRANT_READ_URI_PERMISSION
)
```

### 3. Synthetic Events Are Ephemeral — Capture Early

**Context:** HT-002

React's synthetic event pooling recycles event objects after the handler returns. Accessing `evt.nativeEvent.pageX` inside an async callback? The event is gone.

**What We Learned:**
- **Extract native values synchronously** before any async boundary.
- **This affects all React Native gesture handlers** — not just volume sliders.

**Pattern Established:**
```typescript
// Bad: Async access
sliderRef.current?.measureInWindow((x) => {
  const pageX = evt.nativeEvent.pageX; // evt is recycled — crash
});

// Good: Capture first
const pageX = evt.nativeEvent.pageX;
sliderRef.current?.measureInWindow((x) => {
  // pageX is a safe local copy
});
```

### 4. Cross-Store Consistency Requires Explicit Refresh

**Context:** HT-001, HT-006, HT-015, HT-019

Zustand stores are independent state islands. Deleting a tag in `useTagStore` doesn't automatically update `useButtonStore`. The database knows. The UI doesn't.

**What We Learned:**
- **Foreign key cascades handle DB integrity, not memory.** In-memory stores need explicit cross-store refresh calls.
- **`useFocusEffect` is your friend.** When navigating between tabs, re-fetch data that might have changed elsewhere.
- **Import cross-store dependencies carefully.** Circular imports are easy to create — use dynamic imports or event patterns.

**Pattern Established:**
```typescript
// After deleting a tag
await useButtonStore.getState().removeButtonsForTag(id);
await useButtonStore.getState().loadButtons();
```

### 5. UI State and Business Logic Must Agree on Rules

**Context:** HT-021, HT-024

The "music must flow" principle said exhausted tag pools should auto-reset and keep playing. The service layer (`selectTrackForTag`) implemented this. But `BoardButton.tsx` blocked presses on exhausted buttons. The service was ready — the UI slammed the door.

**What We Learned:**
- **Don't duplicate business logic in UI components.** The service layer decides when to reset; the UI should ask, not guess.
- **"Interactive" and "exhausted" are orthogonal.** A button can be exhausted *and* playing — it needs to accept stop commands.
- **Visual state != interactive state.** Dashed borders and opacity communicate state. Don't let them also block behavior.

**Pattern Established:**
```typescript
// Bad: UI enforces business rule
const isInteractive = !isExhausted;

// Good: UI communicates, service decides
const isInteractive = !isEmpty; // Empty is truly dead; exhausted is recoverable
```

### 6. Safe Area Insets Are Not Optional

**Context:** HT-022, HT-023

Custom headers and hardcoded heights ignore device-specific safe areas. On edge-to-edge displays, content renders behind the status bar. On devices with navigation buttons, tab bars collide with system UI.

**What We Learned:**
- **Always wrap custom headers in `SafeAreaView`.** Especially with `headerShown: false`.
- **Don't hardcode heights for navigation components.** Let the framework calculate safe area padding.
- **Test on multiple device configurations.** Notched phones, button navigation, and software keyboards all behave differently.

**Pattern Established:**
```typescript
// Bad: Ignoring insets
<View style={{ flex: 1 }}>

// Good: Respecting boundaries
<SafeAreaView edges={['top']} style={styles.safeArea}>
```

### 7. Path Traversal Defense Requires Normalization

**Context:** CR-09

String matching for `..` catches the obvious case. But `%2e%2e` (URL-encoded) and `\..` (Windows separators) slip through. Security checks must see through disguises.

**What We Learned:**
- **Decode before you check.** `decodeURIComponent()` first.
- **Normalize separators.** Replace backslashes with forward slashes.
- **Defense-in-depth applies even when threats are unlikely.** SAF URIs are opaque, but the guard should still be competent.

**Pattern Established:**
```typescript
const normalized = decodeURIComponent(path).replace(/\\/g, '/');
if (normalized.includes('..') || normalized.includes('//')) {
  return { isValid: false };
}
```

### 8. Player Queue IDs Must Be Unique Per Play, Not Per Track

**Context:** HT-017

TrackPlayer uses queue item IDs to manage the playlist. Using `track.id` directly means the same track can't appear twice — or be replayed as a direct button — without a collision.

**What We Learned:**
- **Suffix IDs with timestamps** for queue items.
- **Unique-per-play, not unique-per-track.**

**Pattern Established:**
```typescript
await TrackPlayer.add({
  id: `${track.id}-${Date.now()}`,
  url: track.filePath,
  ...
});
```

### 9. Keyboard Avoidance Behavior Differs by Platform

**Context:** HT-003

`KeyboardAvoidingView` with `behavior="height"` on Android caused flickering when combined with bottom-aligned modals. iOS handles it differently.

**What We Learned:**
- **Use `behavior="padding"` on Android** for modals.
- **Test keyboard interactions on both platforms** — they're not symmetrical.

---

### 10. Database Transactions Prevent Orphaned Data

**Context:** CR-01

`setTagsForTrack()` DELETEs all associations then INSERTs new ones. Without a transaction wrapper, a crash between steps orphans the track.

**What We Learned:**
- **Wrap multi-step DB operations in transactions.** `db.withTransactionAsync()`.
- **Test crash recovery scenarios** — not just happy paths.

## Part II: Process Lessons

### 11. Code Review Before Human Testing Catches Architecture Bugs

Bahamut's comprehensive code review identified **65 issues** — including 8 critical — before the first human testing round. Issues like N+1 queries (CR-02), memory leaks (CR-04), and race conditions (CR-08) would have been much harder to diagnose in production.

**Takeaway:** Invest in thorough code review. It's cheaper than debugging production crashes.

---

### 12. Human Testing Surfaces What Code Review Cannot

Code review found the N+1 query. Human testing found that content URIs break the path parser. Both are necessary.

**Bug Discovery by Source:**
- Code Review: Performance, architecture, security patterns
- Human Testing: Platform-specific behavior, UX issues, integration failures

---

### 13. The Trophy Board Preserves Institutional Memory

Each bug got a story — cause, fix, lesson. Six months from now, when someone asks "why is there a timestamp suffix on queue IDs?", the answer is in `BugHuntTrophies.md`.

**Takeaway:** Document *why*, not just *what*. Future maintainers (including yourself) will thank you.

---

### 14. Quick Iteration Beats Perfect Planning

VibeDeck shipped 8 human testing rounds in 4 days. Each round took 30-60 minutes of actual testing. Bugs were fixed the same day. This velocity was only possible because:

- **Builds were automated** (Expo development builds)
- **The council handoff protocol was clear** (architecture → implementation → QA)
- **Scope was ruthlessly controlled** (MVP only — no feature creep)

---

### 15. Native Modules Are A Last Resort, But Sometimes Necessary

We tried pure JavaScript solutions for SAF permissions. They don't exist in Expo's managed workflow. The native module took ~2 hours to build, but solved a blocking issue permanently.

**Takeaway:** Don't fear native code, but exhaust JS options first.

## Part III: Architecture Lessons

### 16. Offline-First Is a Feature, Not a Constraint

VibeDeck's privacy policy (no network calls, ever) was initially framed as a limitation. In practice, it simplified everything:

- No auth flows
- No sync conflicts
- No backend to maintain
- Instant startup
- Works everywhere

**Takeaway:** Constraints can be competitive advantages.

---

### 17. SQLite + Zustand Is a Powerful Combination

SQLite provides durability and complex queries. Zustand provides reactive UI binding. The pattern:

1. **SQLite is the source of truth** for persisted data
2. **Zustand is the source of truth** for UI state
3. **Stores hydrate from SQLite on init** and write-through on mutations

**Gotchas We Discovered:**
- Cross-store refresh must be explicit
- Optimistic updates need rollback handling
- Foreign key cascades only work in the database

---

### 18. Services Should Be Stateless; Stores Should Hold State

The player service initially held `currentTrackRef` as module-level state. This created:
- Testing difficulties (singleton coupling)
- State desync (service vs store)
- Memory leaks (unreleased references)

**Better pattern:** Services execute operations. Stores hold state. Callbacks sync them.

---

### 19. Validation Belongs at System Boundaries

We initially scattered validation throughout the codebase. The cleaner pattern:

- **Import service validates incoming files** (boundary with filesystem)
- **Stores validate incoming data** (boundary with UI)
- **Internal code trusts its inputs** (no redundant checks)

---

### 20. Empty State Design Is Often Overlooked

Three empty states needed explicit handling:
- Empty library (no tracks imported)
- Empty tag (tag exists, no tracks assigned)
- Exhausted tag pool (tracks exist, all played)

Each needed distinct UI treatment. "No Tracks" labels erased button identity (HT-020). The distinction between empty and exhausted drove interactive behavior (HT-021, HT-024).

**Takeaway:** Design empty states as carefully as populated ones.

## Part IV: What We'd Do Differently

### 1. Test Framework Earlier

Jest was configured on day 8 of 10. Earlier setup would have enabled automated regression testing alongside human testing rounds.

### 2. Schema Migration Strategy from Day 1

We punted on database migrations (`SCHEMA_VERSION = 1` with no upgrade path). This is tech debt waiting to bite.

### 3. Type-Safe Event Emitter

Cross-store communication used dynamic imports and `getState()` calls. A type-safe event bus would be cleaner.

### 4. Background Playback from the Start

Deferred to stretch goals, but affects architecture. Should have been scoped earlier.
